# Home Assistant UI and outage QA — 2026-10-16

## Deployed result

Home Assistant local app `local_superlink2mqtt` runs version **0.2.1**, built from
an immutable archive of commit `53f2e0b5713c61b7d82523f172293055cb8cb4fa`.
Start on boot and watchdog remain enabled. The Pi was powered off throughout
this run, as confirmed by the operator.

Before the fix, each failed SSH radio connection escaped `BridgeRuntime.run()`
and exited the process. Supervisor repeatedly restarted it and ultimately
reported an error. Ingress then returned 502; the frontend unconditionally
parsed such responses as JSON. A local proxy returning the exact text
`502: Bad Gateway` reproduced the failure class.

After the fix, repeated failed SSH attempts stayed inside the same running app,
backing off to 30 seconds. The authenticated Ingress panel stayed usable without
entering any bridge or Home Assistant access token. MQTT remained connected;
radio health showed unavailable. The existing device and nine MQTT entities
remained registered. Home Assistant correctly showed the four sensor entities
unavailable and disabled its command buttons.

The device-store SHA-256 stayed unchanged across deployment and retry cycles:
`99a2aa2b7ffc4004dc56988bf0b0c4c75368866c6fccd483760beb17f7679302`.
Private pre-update source and configuration archives are on the HA host under
`/share/superlink-recovery-20261016/`, mode 0600. They are not in Git.

The store catalog must be refreshed with `ha store reload` before a version
update. `ha apps reload` only lists apps and does not refresh this catalog.

## Remaining physical qualification

The powered-off Pi prevents a fresh physical adoption, radio recovery, or sensor
event reaching MQTT/Home Assistant from being verified in this run. When the Pi
is powered on, verify Radio connected, sensor reconnect, a real magnet/button
change, matching HA state, and reconnect after a planned app restart. Software
and simulated-crypto tests do not replace these observations.

The guided SSH key extractor retains its existing limitation: automatic
extraction is not yet qualified on physical Ubiquiti firmware. Initial radio
provisioning still requires the documented private files; missing or invalid
startup configuration is not an interactive onboarding wizard.
